## 二、你提的三个问题（这才是核心）

### 问题1：MCP 工具数量限制 — 你说得对，必须是多个 MCP Server

这个问题击中了当前设计的一个**架构级缺陷**。

**现状问题：**

主流 AI 客户端（Cursor、Claude Desktop、Claw、Dify）连接 MCP Server 时，会调用 `tools/list` 获取所有工具描述，然后**把全部工具描述注入到 LLM 的系统提示中**。这意味着：

```
182个Tool × 每个约 300-500 token（名称+描述+inputSchema+outputSchema）
= 约 55,000 - 90,000 token 仅用于工具描述
```

大多数模型的上下文窗口就被工具描述吃掉一大半，实际对话空间所剩无几。Cursor 等 IDE 也因此限制单个 MCP Server 的工具数为 20-40 个。

**正确架构：每个 Shard = 一个独立的 MCP Server**

```
之前的设计（错误）：
  Claw/Dify ──→ MCP Hub（1个endpoint）──→ 内部路由到 Shard
                 tools/list 返回 182 个 ← 上下文爆炸

正确的设计：
  Claw/Dify ──→ MCP Server: 企微消息（11 tools）
           ──→ MCP Server: ERP-用友（12 tools）
           ──→ MCP Server: RAG（9 tools）
           ──→ MCP Server: ...
                 每个 Server 独立 endpoint，工具数可控
```

这正好和现有的 13 个 Shard 对应。**每个 Shard 就是一个独立的 MCP Server 进程**，有自己的端口和 `tools/list`。

但还需要一个**注册中心/目录服务**，让客户端知道有哪些 MCP Server 可用：

```
MCP Hub 提供两层：

1. 目录层（Hub API，非 MCP 协议）
   GET /api/servers → 返回所有可用 MCP Server 列表
   [
     { name: "企微消息", endpoint: "http://localhost:8090/mcp", tools: 11 },
     { name: "用友ERP", endpoint: "http://localhost:8084/mcp", tools: 12 },
     ...
   ]

2. 执行层（每个 MCP Server，标准 MCP 协议）
   每个 Server 独立暴露 tools/list + tools/call
   客户端按需连接所需的 Server
```

### 问题2：并发能否撑住

分析几个层面：

**单个 MCP Server（Shard）的并发：**
- NestJS 基于 Node.js 事件循环，**I/O 密集型天然支持高并发**
- 每个 Shard 最多 40 个 Tool，实际调用模式是"调用外部 API 然后等响应"
- 这种 I/O 等待型任务，单进程就能处理数百并发
- **不是瓶颈**

**真正的瓶颈在：**

| 瓶颈点 | 场景 | 应对 |
|--------|------|------|
| GPU 模型推理 | 多个 Agent 同时调用 TTS/图像生成 | GPU Scheduler + 队列，按优先级排队 |
| 外部 API 限流 | 企微/用友等有 QPS 限制 | 每个 Connector 内置限流器（令牌桶） |
| AI 生成引擎 | 同时生成多个项目的代码 | BullMQ 队列 + Worker 隔离 |
| PostgreSQL | 审计日志高频写入 | 批量写入 + 异步 flush |

**建议架构：**

```
每个 MCP Server Shard：
├─ 主进程：处理 MCP 协议、路由、鉴权
├─ 连接池：HTTP 复用到外部系统
├─ 本地限流器：per-tool QPS 控制
└─ 如果需要：PM2 cluster 模式多实例
```

实际企业场景中，同时活跃的 Agent 数通常在 5-20 个，不会有互联网级别的并发压力。单进程 + 连接池 + 限流就够了。

### 问题3：配置成功后自动生成多个 Server — 对，必须这样

这是整个 MCP Hub 的**部署核心逻辑**。用户在前端配置完成、测试通过后，点击"发布"：

```
用户点击"发布" → MCP Hub 自动：

1. 分析已启用的配置包，按分类归入 Shard
2. 为每个 Shard 生成独立的 MCP Server 代码包
   ├─ server-wecom-msg/     → 端口 8090，11 个 tools
   ├─ server-erp-yonyou/    → 端口 8084，12 个 tools
   ├─ server-rag/           → 端口 8082，9 个 tools
   └─ ...

3. 自动生成 docker-compose.yml（或更新现有的）
   services:
     mcp-wecom-msg:
       image: mcp-hub/server
       ports: ["8090:3000"]
       volumes: ["./config/wecom-msg:/app/config"]
     mcp-erp-yonyou:

4. 执行 docker-compose up -d
5. 健康检查 → 全部 OK → 注册到目录服务

```
